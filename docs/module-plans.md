## Module B — Board and Management Reporting (BOARD-001..009)

Turns the Xero data the platform already pulls into the board pack the Ramwall board actually reads: a P&L per entity with prior-period and prior-year comparisons, entity account codes rolled up to a single group reporting structure, a consolidated group result with intercompany eliminations shown separately (never silently netted), a WIP-adjusted profit view where every adjustment carries a reason and an approver, and materiality flags so the board sees the movements that matter rather than every line. Output is a web view plus an Excel workbook and a CSV audit detail, both generated from one immutable, checksummed fact set so the numbers on screen, in the spreadsheet and in the commentary are provably the same numbers. Commentary is editable text attached to that locked fact set and can never change a figure.

**Value:** high  |  **Effort:** 17 days

### Tables

- `report_snapshots` — BOARD-001. One immutable header per Xero report pull (P&L, Balance Sheet, Trial Balance) for one entity and period. A refresh inserts a new row; rows are never updated, so an old board pack still resolves to the evidence it was built from (spec 14.7 'immutable by run').
  - columns: `id`, `entity_id -> entities.id`, `report_type ('profit_and_loss'|'balance_sheet'|'trial_balance')`, `period_start (date-only)`, `period_end (date-only)`, `timeframe ('MONTH'|'QUARTER'|'YEAR')`, `periods (integer, comparison columns requested)`, `tracking_category_id (nullable)`, `tracking_option_id (nullable)`, `xero_app_id`, `connection_id`, `tenant_id`, `sync_run_id -> sync_runs.id`, `xero_report_id`, `xero_report_name`, `xero_report_date`, `row_count`, `created_at`, `updated_at`
- `report_rows` — BOARD-001/003/006. One row per account per report column, stored long rather than wide so changing the number of comparison columns is a data change, not a migration. This is the drill-through target for every group figure and every commentary citation.
  - columns: `id`, `report_snapshot_id -> report_snapshots.id`, `section_title`, `row_order (integer, preserves Xero's own ordering)`, `account_code`, `account_name`, `xero_account_id (nullable, Xero omits it on subtotal rows)`, `column_key ('current'|'prior_period'|'prior_year')`, `column_period_start (date-only)`, `column_period_end (date-only)`, `amount (decimal string)`, `currency`, `is_subtotal (boolean)`, `created_at`
- `group_accounts` — BOARD-002. The target group reporting chart — the codes the board sees, independent of any entity's Xero chart. Small, hand-maintained reference table.
  - columns: `id`, `group_code (unique)`, `group_name`, `statement ('profit_and_loss'|'balance_sheet')`, `parent_group_code (nullable, self-referencing for subtotals)`, `sort_order (integer)`, `sign ('natural'|'invert')`, `created_at`, `updated_at`
- `group_account_map_versions` — BOARD-002. Makes mapping changes versioned and effective-dated. A board pack records which version it used, so a re-run of an old period reproduces the old numbers.
  - columns: `id`, `version (integer, unique)`, `status ('draft'|'approved'|'superseded')`, `effective_from (date-only)`, `effective_to (date-only, nullable)`, `approved_by_email (nullable)`, `approved_at (nullable)`, `notes`, `created_at`, `updated_at`
- `group_account_mappings` — BOARD-002. The (entity, account code) -> group code rows belonging to one map version. entity_id uses the literal '*' sentinel already exported from db/schema.ts as GLOBAL_THRESHOLD_SCOPE for a group-wide default mapping, for the same reason it exists there: SQLite treats NULLs as distinct in a unique index, so a nullable 'applies to all' row could silently duplicate.
  - columns: `id`, `map_version_id -> group_account_map_versions.id`, `entity_id (entity id or '*')`, `account_code`, `group_code -> group_accounts.group_code`, `created_at`, `updated_at`, `unique index (map_version_id, entity_id, account_code)`
- `consolidation_eliminations` — BOARD-003. Explicit elimination entries against a group code for a period. Unresolved differences are deliberately NOT a table — they are computed as gross group total per counterparty pair minus approved eliminations, so a difference cannot be made to disappear by deleting a row.
  - columns: `id`, `period_start (date-only)`, `period_end (date-only)`, `group_code -> group_accounts.group_code`, `entity_id -> entities.id`, `counterparty_entity_id -> entities.id`, `amount (decimal string)`, `currency`, `source ('manual'|'intercompany_match')`, `source_ref (nullable, holds the Module G match id later)`, `status ('proposed'|'approved'|'rejected')`, `reason`, `created_by_email`, `approved_by_email (nullable)`, `approved_at (nullable)`, `created_at`, `updated_at`
- `management_adjustments` — BOARD-007. One approved management adjustment (e.g. excluding development WIP from operating profit). Carries every field the requirement names: id, entity, period, account/group line, amount, reason, approver. The before/after view is computed from this plus the snapshot, not stored twice.
  - columns: `id`, `adjustment_key (unique, human reference e.g. 'WIP-EXCL-RD-2026-03')`, `entity_id -> entities.id`, `period_start (date-only)`, `period_end (date-only)`, `group_code (nullable)`, `account_code (nullable)`, `amount (decimal string)`, `currency`, `adjustment_type ('wip_exclusion'|'reclass'|'accrual'|'other')`, `reason (not null)`, `status ('draft'|'approved'|'rejected'|'reversed')`, `source_report_snapshot_id -> report_snapshots.id (the 'before' evidence)`, `created_by_email`, `approved_by_email (nullable)`, `approved_at (nullable)`, `created_at`, `updated_at`
- `board_pack_runs` — BOARD-005/008/009. One generation of the pack. facts_checksum is the SHA-256 of the assembled fact set and is what makes BOARD-009's 'locked structured fact set' enforceable: if the underlying data moves, the checksum no longer matches and the commentary is marked stale rather than quietly wrong.
  - columns: `id`, `period_start (date-only)`, `period_end (date-only)`, `basis ('actual'|'adjusted')`, `map_version_id -> group_account_map_versions.id`, `status ('draft'|'released')`, `facts_checksum`, `generated_by_email`, `generated_at`, `released_by_email (nullable)`, `released_at (nullable)`, `notes`, `created_at`, `updated_at`
- `board_pack_sections` — BOARD-005/009. The twelve seeded sections in order, each holding its own locked fact JSON and its commentary. Commentary lives here and nowhere near the numbers, so editing it can never move a figure.
  - columns: `id`, `board_pack_run_id -> board_pack_runs.id`, `section_key ('executive_summary'|'cash_and_liquidity'|'management_accounts'|'adjusted_group_profit'|'entity_review'|'project_view'|'balance_sheet_recs'|'debt_and_funding'|'stress_test'|'change_from_prior'|'interest_rate_position'|'risks_and_actions')`, `section_order (integer)`, `title`, `status ('pending'|'ready'|'not_applicable')`, `facts_json (JSON string: the section's locked rows and metrics, each with a citable row id)`, `commentary_draft (nullable)`, `commentary_final (nullable)`, `commentary_edited_by_email (nullable)`, `commentary_edited_at (nullable)`, `created_at`, `updated_at`, `unique index (board_pack_run_id, section_key)`
- `variance_thresholds (ALTER, not a new table)` — BOARD-006 reuses the existing CASH-005 table instead of adding a parallel materiality table. Add one column and widen one index; nothing else changes. Existing CASH-005 callers keep working because the new column defaults to 'cash'.
  - columns: `ADD context text not null default 'cash' ('cash'|'pnl_movement'|'budget_variance')`, `DROP unique index variance_thresholds_scope_unique`, `ADD unique index variance_thresholds_scope_context_unique on (entity_id, context)`

### Routes

- `POST /api/xero/sync/reports` — Admin. Pulls P&L (and optionally Balance Sheet / tracking-filtered P&L) for one entity and period into report_snapshots + report_rows. Copies the exact shape of app/api/xero/sync/route.ts: open a sync_runs row, resolveXeroRoute -> getAuthenticatedClient, write with full lineage (xero_app_id, connection_id, tenant_id, sync_run_id per spec 10.5), close the run, update xero_connections health, recordAuditEvent on both paths.
- `GET /api/reports/pnl` — BOARD-001. ?entityId=&periodStart=&periodEnd=&compare=prior_period|prior_year|both. Reads the latest report_snapshot for each window and returns account rows plus comparison columns and movements. Viewer role.
- `GET /api/reports/group-map` — BOARD-002. ?asOf=YYYY-MM-DD. Returns the effective map version, its mappings, and the list of entity account codes present in report_rows but unmapped — the unmapped list is the whole point, an unmapped code must be visible, not silently dropped from the group total.
- `POST /api/reports/group-map` — BOARD-002. Admin. Creates a new draft map version (optionally cloned from the current one) with its mapping rows. Never edits an approved version.
- `PATCH /api/reports/group-map/[versionId]` — BOARD-002. Admin. {status:'approved', effectiveFrom} — approves a draft, stamps approved_by_email/approved_at, and closes the previous version's effective_to the day before. Audited.
- `GET /api/reports/consolidation` — BOARD-003. ?periodStart=&periodEnd=&basis=actual|adjusted. Returns all five layers the requirement names: entity-level results, gross group aggregation before eliminations, the elimination entries, the consolidated result, and unresolved elimination differences per counterparty pair.
- `GET /api/reports/eliminations` — BOARD-003. ?periodStart=&periodEnd=&status=. Lists elimination entries with their counterparty pair and approval state.
- `POST /api/reports/eliminations` — BOARD-003. Admin. Creates a proposed elimination entry (source='manual' for this module; source='intercompany_match' arrives with Module G).
- `PATCH /api/reports/eliminations/[id]` — BOARD-003. Admin. {status:'approved'|'rejected'} with approver stamping. Only approved entries reduce the consolidated result; proposed ones show but do not eliminate.
- `GET /api/reports/tracking` — BOARD-004. ?entityId=&periodStart=&periodEnd=. Returns the tracking-option breakdown from tracking-filtered P&L snapshots, joined to the Ramwall/Wunderbuild project code map. Returns an explicit 'tracking not configured for this org' state rather than an empty grid.
- `GET /api/reports/adjustments` — BOARD-007. ?entityId=&periodStart=&periodEnd=&status=. Lists management adjustments with reason and approver.
- `POST /api/reports/adjustments` — BOARD-007. Admin. Creates a draft adjustment. Rejects a missing or empty reason at the boundary — a WIP exclusion without a stated reason is exactly the thing an auditor asks about.
- `PATCH /api/reports/adjustments/[id]` — BOARD-007. Admin. {status:'approved'|'rejected'|'reversed'} with approver stamping. Audited.
- `GET /api/reports/materiality` — BOARD-006. ?periodStart=&periodEnd=&entityId=. Returns movements classified by trigger: absolute amount, percentage change, variance to budget (null until Module C), new account/activity, and recurring vs one-off.
- `GET /api/board-packs` — BOARD-005. Lists runs with period, basis, status and generated/released stamps.
- `POST /api/board-packs` — BOARD-005/009. Admin. Assembles the fact set for a period, seeds all twelve sections in order, computes and stores facts_checksum. This is the lock: after this call the numbers in the pack are fixed.
- `GET /api/board-packs/[runId]` — BOARD-005. Returns the run, its sections in order, each section's facts and commentary, and a stale flag if a recompute of facts_checksum no longer matches.
- `PATCH /api/board-packs/[runId]` — BOARD-005. Admin. {status:'released'} with releaser stamping. A released run is read-only.
- `PATCH /api/board-packs/[runId]/sections/[sectionKey]` — BOARD-009. Admin. Edits commentary_draft/commentary_final only. ### Risks

- The granular report scope strings in read_core_v1 do not match Xero's published OAuth2 scope list as I understand it — Xero exposes a single accounting.reports.read covering P&L, Balance Sheet, Trial Balance and Bank Summary, not per-report scopes like accounting.reports.profitandloss.read. Verify with one authorize URL against the Demo Company before writing any Module B sync code — it is a ten-minute check that gates the whole module. Same doubt applies to accounting.invoices.read / accounting.payments.read / accounting.banktransactions.read / accounting.manualjournals.read, which I believe collapse into accounting.transactions.read.
- accounting.journals.read is forbidden by spec line 791, so there is no journal-level drill-through. BOARD-003's unresolved elimination differences can only be reported at group-code and account-code granularity, never down to the journal line that caused them. The client should be told this before they see the first unexplained difference and ask 'which transaction'.
- report_rows will be the largest table in the build — roughly (accounts x comparison columns x entities x periods). Ten entities, 200 accounts, 3 columns, 24 months is about 144k rows, fine on SQLite and fine on D1, but the immutability rule means it only ever grows. Add a retention decision before the first year-end, not after.
- BOARD-004 is conditional on tracking being configured and applied consistently in each org. If Ramwall's entities tag some transactions and not others, the tracking breakdown will not sum to the P&L total, and that discrepancy will read as a bug rather than as a data-quality finding. Surface the unallocated remainder as an explicit line rather than letting it vanish.
- BOARD-008 Excel needs one new dependency (exceljs — multi-sheet plus number formats; SheetJS's maintained build is no longer on the public npm registry, so it is the wrong pick here). CSV needs none. If a dependency is unwelcome, ship CSV first and add xlsx when the template arrives — the template is a blocker for the workbook anyway.
- BOARD-009's fact-set lock is only as strong as the checksum. If a section's facts_json is assembled non-deterministically (map iteration order, unsorted rows, floating timestamps) the checksum will churn and every pack will look stale. Sort deterministically and exclude generation timestamps from the hashed payload; this is the kind of thing that is cheap now and a two-day debug later.
- BOARD-006's 'recurring versus one-off' is the only requirement in the module with no defensible default. Any heuristic invented here becomes accounting policy by accident, which is precisely what REM-001 forbids. Leave it unimplemented and visibly marked 'awaiting client rule' rather than guessing.
- Group mapping versions are effective-dated, and a board pack pins map_version_id — but management_adjustments and consolidation_eliminations reference group_code as a plain string, not a version. If a group code is renamed between versions, historical adjustments dangle. Either treat group codes as immutable once approved (simplest, recommended) or the rename path needs handling.

## Module C — P&L Movement and Budget Variance (VAR-001..VAR-004)

Pulls each entity's monthly Profit & Loss from Xero into immutable, dated snapshots, then compares any month against the prior month, the same month last year, prior-year year-to-date, or an approved budget — with the movement, the percentage, and whether it breaches the entity's materiality threshold. Budgets come from Xero where the tenant actually holds enough detail, otherwise from the approved budget workbook uploaded as a versioned, approval-dated file. Explanations typed by a person are stored in their own table and never touch the calculated numbers, so a figure on screen can always be traced back to the exact Xero sync that produced it.

**Value:** high  |  **Effort:** 12 days

### Tables

- `report_snapshots` — One immutable record per P&L fetch (spec 14.7: a refresh creates a new snapshot, never overwrites). Holds the report parameters that determine what the numbers mean, plus full spec 10.5 lineage. Insert-only; the read model picks the newest snapshot covering the requested period.
  - columns: `id`, `entity_id -> entities.id`, `report_type (enum: profit_and_loss)`, `xero_app_id`, `connection_id`, `tenant_id`, `sync_run_id -> sync_runs.id`, `period_start (date-only)`, `period_end (date-only)`, `timeframe (enum: MONTH/QUARTER/YEAR, default MONTH)`, `period_count (integer)`, `basis (enum: accrual/cash — Xero paymentsOnly)`, `standard_layout (boolean, default true)`, `tracking_category_id (nullable)`, `tracking_option_id (nullable)`, `report_title`, `report_date (Xero's ReportDate string, verbatim)`, `parser_version`, `row_count`, `created_at`, `updated_at`
- `report_rows` — The P&L actuals, normalised long: one row per (snapshot, section, account, month). Every VAR-001 comparison and the VAR-003 ranking is arithmetic over this one table, so no second shape is needed for movement vs YTD vs budget.
  - columns: `id`, `report_snapshot_id -> report_snapshots.id`, `section (Xero section title verbatim, e.g. 'Less Operating Expenses')`, `section_kind (enum: revenue/cost_of_sales/operating_expense/other_income/other_expense/total/unclassified — drives the favourable/adverse sign)`, `xero_account_id (nullable; null on computed/total rows)`, `account_code (nullable)`, `account_name`, `period (YYYY-MM month key)`, `amount (decimal string via Money.toStorageString())`, `currency (default NZD, sourced from entities.reporting_currency)`, `created_at`, `updated_at`, `unique (report_snapshot_id, section, account_name, period)`, `index (report_snapshot_id, period)`
- `budget_snapshots` — One versioned budget per entity from either VAR-002 source, carrying the version label and approval date VAR-002.3 requires. Xero-sourced rows carry lineage; workbook-sourced rows carry file key + checksum exactly like bank_imports does.
  - columns: `id`, `entity_id -> entities.id`, `source (enum: xero/workbook)`, `xero_budget_id (nullable)`, `budget_type (enum: OVERALL/TRACKING, nullable)`, `xero_app_id (nullable)`, `connection_id (nullable)`, `tenant_id (nullable)`, `sync_run_id -> sync_runs.id (nullable)`, `source_file_key (nullable)`, `source_file_checksum (nullable)`, `parser_version (nullable)`, `name`, `version_label`, `approved_at (date-only, nullable until approved)`, `approved_by_email (nullable)`, `status (enum: draft/approved/superseded, default draft)`, `covers_from (date-only)`, `covers_to (date-only)`, `uploaded_by_email`, `created_at`, `updated_at`, `index (entity_id, status, covers_to)`
- `budget_rows` — Budget amounts, same long shape as report_rows so the variance calculation joins actual to budget on (account_code, period) with no source-specific branching.
  - columns: `id`, `budget_snapshot_id -> budget_snapshots.id`, `account_code (notNull — the join key; the parser must supply one)`, `xero_account_id (nullable)`, `account_name (nullable)`, `period (YYYY-MM)`, `amount (decimal string)`, `tracking_option_id (notNull, default '*' sentinel — nullable columns in a SQLite unique index are treated as distinct, the same trap db/schema.ts already documents for GLOBAL_THRESHOLD_SCOPE)`, `tracking_category_id (nullable)`, `notes (nullable)`, `source_row_ref (workbook row reference, mirrors bank_balance_snapshots.source_row_ref)`, `created_at`, `updated_at`, `unique (budget_snapshot_id, account_code, period, tracking_option_id)`
- `variance_commentary` — VAR-004: human or AI explanation, stored in its own table and never read by the calculation path. The API returns it under a separate key so a commentary row can never alter a number.
  - columns: `id`, `entity_id -> entities.id`, `period (YYYY-MM)`, `comparison (enum: prior_month/prior_year_month/prior_year_ytd/budget/custom)`, `account_code (notNull; '*' sentinel = whole-entity narrative)`, `origin (enum: user/ai, default user)`, `body`, `cited_row_ids (JSON array of report_rows.id / budget_rows.id — enforces the BOARD-009 'cite the rows used' rule)`, `author_email`, `status (enum: draft/final/superseded, default draft)`, `created_at`, `updated_at`, `index (entity_id, period, account_code)`

- Xero caps the P&L report's periods parameter at 11, so covering the current month plus prior-year comparatives takes 2-3 calls per entity, not one. Still comfortably inside the 5,000/day/tenant limit and the spec's 20% reserve, but the fetch loop must be written expecting multiple calls.
- The Xero Budgets API may not return usable detail — VAR-002.1 exists precisely because this is unproven. Until the capability test runs, the budget half of this module cannot be called schedule-safe, and the workbook importer is on the critical path regardless.
- A period restated in Xero after a snapshot was taken means stored actuals silently diverge from Xero. Mitigation: surface a stale/oldestSourceDate signal the same way app/api/cash-position/route.ts does, and never update a snapshot in place.
- report_snapshots immutability is a convention, not a constraint — one stray db.update() destroys the evidence trail. Cheap to guard with a test that re-syncing the same period produces two snapshot rows, not one.
- Multi-currency: Money.of enforces matching currencies and throws on add(). Read the currency from entities.reporting_currency rather than hard-coding NZD, or a tenant with foreign-currency accounts throws at aggregation time.
- Scope creep from Module B — BOARD-006 wants the same materiality ranking. Build it here as a pure lib module and Module B imports it; do not let a board-pack requirement widen this module's surface.

## Module E — Rules and Categorisation Exceptions (RULE-001..004)

Turns Ramwall's accounting policy into data instead of code: each rule (e.g. "a GST-bearing construction cost must carry a project code") is stored as a versioned, dated, approved record, and the engine runs those rules over synced Xero invoice lines to raise exceptions. Every exception carries a deterministic explanation, frozen evidence of the figures it was based on, and a triage workflow from detected through to closed, with every status change audited. It is read-and-flag only: it never writes anything back to Xero and never decides a code itself.

**Value:** high  |  **Effort:** 15 days

### Routes

- `GET /api/rules` — Rule catalogue: each definition with its currently approved version, effective dates, severity, materiality and approval state. Also returns coverage counts (approved / draft / blocked) so nobody can believe the engine is running when 11 of 13 rules are still drafts. requireSession() — viewer.
- `POST /api/rules` — Create or update a rule definition (name, description, category, owner, enabled). requireSession("admin"), audited as rule_definition.updated. Zod-validated like /api/thresholds.
- `POST /api/rules/versions` — Create a draft version of a rule (conditions, severity, materiality, evidence requirements, recommended action, entity scope, effective dates). Conditions are validated against lib/rules/conditions.ts at save time so a malformed rule is rejected here, not mid-run. requireSession("admin").
- `POST /api/rules/versions/[versionId]/approve` — Approve or reject a draft version (RULE-001 approval). Approver must differ from created_by_email — segregation of duties. Supersedes the previous approved version of the same definition in one transaction. requireSession("admin"), audited as rule_version.approved with from/to like the thresholds route.
- `POST /api/xero/sync/invoices` — PREREQUISITE sync. Pulls invoices and credit notes plus line items for one entity into xero_invoices / xero_invoice_lines with lineage, paged and incremental via If-Modified-Since. Sits beside the existing /api/xero/sync route rather than bloating it, and reuses resolveXeroRoute + getAuthenticatedClient + the sync_runs bookkeeping and failure handling verbatim. requireSession("admin").
- `POST /api/rules/run` — Run the engine for { entityId, periodStart, periodEnd }. Creates a rule_runs row, loads local facts (no Xero call except one TaxRates read), calls the pure evaluator, upserts exceptions by fingerprint and writes exception_evidence. requireSession("admin"), audited as rule_run.complete / rule_run.failed.
- `GET /api/exceptions` — Triage queue, filterable by entityId, status, severity, ruleKey and period. requireSession() — viewer. There is deliberately no POST: an exception can only be created by a rule run.
- `GET /api/exceptions/[exceptionId]` — One exception with its evidence rows, the rule version that raised it, and its audit trail (status changes and notes read back from audit_events by resource_id). requireSession() — viewer.
- `PATCH /api/exceptions/[exceptionId]` — RULE-004 lifecycle: status transition, assignment, resolution note, optional LLM explanation. The transition is validated by lib/rules/lifecycle.ts, never by the client or the page. Every change is audited as exception.status_changed with from/to. requireSession("admin").

### Logic modules

- lib/rules/catalogue.ts — the 13 RULE-002 rule keys as constants, each with a small pure predicate over { invoice, lines, supplierProfile, validTaxTypes, conditions }. A plain Record of key -> evaluator; no plugin framework, no class hierarchy.
- lib/rules/conditions.ts — zod schema per rule for the rule_versions.conditions JSON (account-code sets, tracking category name, minimum sample size, recency half-life, duplicate window in days). Used both at save time and at load time so a bad rule fails closed.
- lib/rules/evaluate.ts — the pure orchestrator: selectActiveVersions(defs, versions, entityId, asAtDate) fails closed on two versions effective for the same rule+entity+date (same discipline as resolveXeroRoute), then maps facts to DetectedException[] with fingerprint and materiality. No db import, no fetch — fully unit testable.
- lib/rules/supplierProfile.ts — RULE-003 deterministic statistics per (entity, contact): dominant account code, dominant tax type, dominant tracking option, amount distribution (median + median absolute deviation, robust to one large bill), entity-specific behaviour and exponential recency weighting. Decimal-only via lib/money.ts. Abstains below the configured minimum sample rather than guessing (BS-005).
- lib/rules/lifecycle.ts — the RULE-004 status graph as a pure Record<status, status[]> plus canTransition(). This is the REM-001 boundary: the exceptions page renders whatever buttons this module permits and hardcodes none of them.
- lib/xero/invoiceSync.ts — paging, where-clause construction, response-to-row mapping and payload hashing for invoices and credit notes. Extracted from the route because it needs pagination and its own tests; the route keeps the sync_runs + connection-status bookkeeping.

### Risks

- read_core_v1 probably contains scope strings Xero will reject or ignore (accounting.invoices.read and the granular accounting.reports.* set). Fix is a new read_core_v2 profile containing accounting.transactions.read plus a re-authorisation of every connection — which is itself a reviewable compliance event through buildXeroClient's 9.6 gate, never an in-place edit of v1. xero_connections already has the permission_missing status for the failure mode.
- The first bulk backfill is the riskiest call this build has ever made against the client's real tenants: Xero allows 60 calls/minute and 5,000/day per tenant, and there is no rate-budget table yet. Mitigation is sequential paging, If-Modified-Since incremental runs after the first, and a partial status on rule_runs and sync_runs rather than an all-or-nothing failure.
- Xero's list-invoice response shape is unverified in this codebase: line items are returned only under paging, and a summaryOnly response would silently produce zero lines and therefore zero exceptions — an engine that looks healthy and finds nothing. Same class of assumption already flagged in lib/xero/reports.ts:9. Verify against the Demo Company and assert lines-per-invoice > 0 in the sync before locking the parser.
- Silent inertness: with 11 of 13 rules unapproved, a run completes successfully and raises nothing. Mitigated by rule_runs.rule_version_ids recording exactly what was applied, and /api/rules returning explicit approved/draft/blocked coverage that the rules page must show.
- Fingerprint churn — if the dedup key included rule_version_id, every approved policy edit would orphan open exceptions and re-raise them as new. The fingerprint therefore hashes the rule *key*, not the version.
- False positives from thin supplier history: three bills have no meaningful dominant code. The minimum-sample floor lives in the rule conditions and the rule abstains below it — BS-005 'no false completeness' applies to rules as much as to reconciliations.
- Storing credit notes in xero_invoices with a document_kind column deviates from the spec 14.6 list, which names xero_credit_notes separately. Chosen because the shape is identical and duplicate detection wants one query; call it out for review before the migration is generated.
- The explanation column is a standing temptation. RULE-003 is explicit that an LLM may explain but must never decide, so the PATCH route must accept explanation/explanation_model only and must never let that path touch status, severity or any account code. Worth a dedicated test rather than a comment.
- Effort of 15 days assumes the client answers question 14 during the build. If the rule catalogue arrives late, everything ships except live rule content and the module demos against seeded draft rules — real value slips to whenever the policy lands.

## F — Intercompany Reconciliation

Module F reconciles transactions between Ramwall group entities from both sides at once — a Ramwall recharge invoice is matched against the bill the receiving entity recorded, a CHH Trust loan drawdown against the borrowing entity's entry. It refuses, by design, to report anything as reconciled when only one of the two entities is connected to Xero, so the group can never be shown a clean intercompany position that is really just a one-sided guess. The output is a pair matrix (every approved relationship, its net difference and whether both sides are readable) plus a drillable workpaper per pair showing which documents matched, at what confidence tier, and what remains unexplained.

**Value:** high  |  **Effort:** 14 days

Pure.

### Blocked on client decisions

- Which legal entities actually have their own Xero organisation. Every row in `entities` is still status='unverified'. A pair matrix built over unverified entities reconciles nothing real.
- The approved relationship list itself (IC-002, and spec Part XVII item 18 'Approve intercompany relationship registry'): which entity pairs, and which of recharge / treasury_loan / management_fee / property each is. This cannot be inferred from the data — an unapproved pair that happens to trade is not an intercompany relationship.
- Per pair, the Xero **Contact ID** representing each entity inside the counterparty's organisation, and the **intercompany control account code** each side posts to. IC-002 explicitly forbids relying on contact names, and these IDs can only be read by someone with access to each Xero org. Without them the matcher has no entry point and every pair returns empty.
- Expected margin policy and GST basis per recharge relationship (IC-008; spec Part XVII item 19). checkRechargePolicy() cannot say whether a 12% uplift is correct or a breach without the policy.
- The date tolerance for a timing difference (IC-003 tiers 2, 3 and 5) and how a period boundary is treated. Seven days is a placeholder default, not a client decision.
- Which entities get the Starter app's five connection slots (spec 7.5). This single choice decides how many pairs Module F can reconcile at all — every other pair will correctly and permanently report 'one side not connected'.
- Whether and when the client will run a reauthorisation round across all connected organisations for the corrected scope profile. Until that happens Module F cannot read invoices, and neither can anything else.
- CHH Trust loan terms: interest rate, capitalisation frequency and fee schedule. IC-007 requires distinguishing capitalised interest from principal, and there is no way to do that from a journal amount alone.
- Whether an intercompany amount difference should use the existing CASH-005 threshold for the originating entity, or its own materiality figure per pair. The design defaults to reusing CASH-005; confirm before the pilot.

### Risks

- The scope defect gates everything. Until read_core_v2 is approved and every organisation is reauthorised, Module F reads zero transactions and cannot be demonstrated. Sequence this first, not last — it has a client-calendar dependency, not just a code one.
- IC-003 tier 4 (grouped one-to-many / many-to-one) is a subset-sum problem. A naive search over a busy control account will not terminate. Bound it: same contact, same calendar month, maximum group size 4, greedy largest-first. Anything outside those bounds falls to tier 6 'probable' or tier 7 'unmatched' and goes to a human. The ceiling is deliberate and should be stated in the code comment, with 'raise the bound or add a real solver' as the upgrade path.
- No pagination or rate-limit handling exists anywhere in the current sync path — app/api/xero/sync/route.ts calls getAccounts once, unpaged. Xero allows 60 calls/minute and 5,000/day per tenant, and /Invoices pages at 100. An intercompany backfill across several entities and six resources will hit the daily cap on a real organisation. Pagination and a 429/Retry-After backoff must be built as part of the intercompany sync route, and is a meaningful slice of the 14 days.
- Contact-ID drift. If an entity is re-created as a new contact in the counterparty's Xero org, the relationship silently returns nothing. Mitigation: never fall back to name matching (IC-002 forbids it), and surface 'relationship has no matching contact in this tenant' as an explicit registry health state rather than an empty, innocuous-looking result.
- intercompany_items duplicates data that Module D's xero_invoices / xero_bank_transactions will eventually own (spec 14.6). Accepted deliberately: Module F needs a counterparty-facing normalised view with signed_total and relationship attribution that the raw tables would not carry. When Module D lands, intercompany_items becomes a projection over those tables, not a second sync. Write that down now or the group ends up with two truths about the same invoice.
- Cross-app pairs (spec 7.7). resolveXeroRoute is per-entity so a pair spanning two Xero apps already works, but a match run then touches two authorisations and either can be stale or rate-limited independently. intercompany_match_runs records both sides' connection and staleness for exactly this reason — a run must never average away one side's staleness.
- False reconciliation is the highest-severity row in the spec's own risk table. The IC-001 gate therefore lives in lib/intercompany/pairing.ts and is called before any match row is written, not checked in the UI or the route body — a second caller added later must hit the same gate.
- Manual journals frequently carry no contact, so IC-007 one-sided journals can only be attributed by account code. Those are structurally lower confidence and should land at tier 6 'needs review' by construction rather than being force-matched on amount alone.
- Everything downstream of the registry is only as good as the client-supplied contact IDs and account codes. If those arrive incomplete, the pilot demonstrates the refusal path (which is genuine value and an IC-009 acceptance item) but not the matching path. Budget a working session with whoever holds Xero access rather than assuming a spreadsheet will arrive.

## G — GST Audit and Reconciliation

Gives Ramwall a per-entity, per-GST-period audit of the return before it is filed. It reads every GST-bearing transaction out of Xero (invoices, credit notes, spend/receive money, manual journals, prepayments/overpayments, payments), recalculates the GST position deterministically in Decimal, and reconciles that figure against either the finalised Xero GST report or the GST control account, showing the unresolved difference. Every flagged item — a missing project code, a wrong tax type, a duplicate bill, a transaction outside the period — carries full drill-through evidence back to the Xero organisation, document number, contact, account, tax type and sync run that produced it.

**Value:** high  |  **Effort:** 15 days

### Risks

- HARD BLOCKER — scope gap. read_core_v1 contains no accounting.transactions.read, and the granular names it does contain (accounting.invoices.read, accounting.payments.read, accounting.banktransactions.read, accounting.manualjournals.read) are not strings Xero's OAuth 2.0 scope list issues; Xero's documented scope covering Invoices, CreditNotes, BankTransactions, ManualJournals, Prepayments, Overpayments and Payments is the single accounting.transactions.read. Likewise the per-report scopes (accounting.reports.balancesheet.read, ...trialbalance.read, ...taxreports.read) collapse to accounting.reports.read. Under the profile as written Module G can read zero transactions. Fix is cheap in code (read_core_v2) and expensive operationally: every connection must re-consent. Verify against Xero's live consent screen before anything else in this module is built.
- No GST report endpoint exists. xero-node's accountingApi exposes only AgedPayables/AgedReceivables/BalanceSheet/BankSummary/BudgetSummary/ExecutiveSummary/ProfitAndLoss/TenNinetyNine/TrialBalance/ReportFromId/ReportsList — there is no getReportGst. Spec 3.8's claim that finalised NZ GST reports are available rests entirely on getReportsList returning the filed return, which is unverified. If it does not, GST-001 finalised mode is upload-only and gst_return_imports.source is always 'upload'.
- xero-node types every money field as a JS number (LineItem.taxAmount is `number`). Amounts must be converted per value with Money.of(String(value)) at the ingest boundary and stored via toStorageString() at 4dp; the raw numbers must never be summed. Request unitdp=4 on every paged call.
- Payments-basis reconstruction is the hardest part of GST-002 and the most likely source of a wrong number: partial payments split one document's GST across periods, and prepayments/overpayments allocate later. Budget the time here, and label any payments-basis result as reconstructed even when a finalised return exists.
- Voided and deleted documents do not reliably resurface through ifModifiedSince, so a run must re-read the whole period rather than sync incrementally, and mark absent documents by source status rather than deleting rows (spec 1377). A document voided after a run must not silently change a historical run's totals — this is why gst_runs and gst_run_totals are immutable per run.
- Tracking category and option names are free text controlled by the client's Xero setup, so the missing-project-code rule is only as good as the naming convention; it belongs in gst_rule_settings.params_json, never in the rule code.
- GST-007: reserved accounts (bank, AR, AP, retained earnings) cannot appear in manual journal lines, so not every GST correction is journalable. The UI must not present a proposed fix as executable — and with no write scopes anywhere in this build, no finding ever posts anything back to Xero. The proposed_fix / pending_approval statuses are workflow labels only.
- Reconstructed figures being read as filed figures is the main correctness risk to the client. Mode must be stamped on the run row, on every API payload, on the UI header and in the CSV export header — not inferred at the presentation layer.
- Xero's 60 calls/minute and 5,000/day per-tenant limits with 100 rows per page: a two-month period across five entities is comfortable, a multi-year historical backfill for the regression fixture is not. The sync route needs paging with a retry on 429 honouring Retry-After.

## Module H — Debt, Funding and Lender View (DEBT-001..005)

Turns the Ramwall Loan Register from a spreadsheet into a live lender view: every facility by entity and lender with limit, drawn, available, fixed/floating split, rate, maturity, P&I-vs-interest-only, security group and covenant threshold, all traceable to the register file it came from. It compares each facility's register balance against the matching Xero loan and interest accounts and flags material differences using the same variance-threshold policy Module A already uses for cash. It runs configurable covenant and stress tests (LVR by charging group, rate sensitivity, upcoming expiries, liquidity after committed payments) with no threshold hard-coded, and keeps an evidenced, period-approved schedule of lender reporting adjustments.

**Value:** high  |  **Effort:** 14 days

### Tables

- `loan_register_snapshots` — DEBT-001 — one immutable row per uploaded Loan Register file. Deliberately a near-copy of bank_imports so the register is replayable and every facility figure traces to a checksummed source file. Group-scoped (no entity_id) because one register covers all entities; entity lives on the facility row.
  - columns: `id (text pk)`, `source_file_key (text notNull)`, `source_file_checksum (text notNull)`, `register_as_at (text notNull, date-only — the register's own source date, DEBT-002 'source date')`, `file_received_at (text notNull, UTC ISO)`, `processed_at (text)`, `imported_by_email (text notNull)`, `parser_version (text notNull)`, `status (text enum received|parsed|failed|superseded, default received)`, `error (text)`, `created_at / updated_at`
- `loan_facilities` — DEBT-002 — one row per facility per snapshot. Never mutated: a new register upload writes a new snapshot's rows, so historic covenant results stay reproducible. available_amount is NOT stored — it is limit minus drawn, derived in lib/debt/facilityView.ts (REM-001).
  - columns: `id (text pk)`, `snapshot_id (text notNull → loan_register_snapshots.id)`, `entity_id (text notNull → entities.id)`, `lender_name (text notNull)`, `facility_reference (text notNull)`, `facility_type (text — e.g. term, revolving, overdraft)`, `security_group (text — e.g. 'ASB charging group', the LVR scope key)`, `facility_limit (text notNull, decimal string)`, `drawn_balance (text notNull, decimal string)`, `currency (text notNull default 'NZD')`, `repayment_basis (text enum principal_and_interest|interest_only|unknown, default unknown)`, `maturity_date (text, date-only)`, `review_date (text, date-only)`, `entity_bank_account_id (text → entity_bank_accounts.id, nullable; links to the existing is_loan_facility rows)`, `xero_loan_account_code (text)`, `xero_interest_account_code (text)`, `source_row_ref (text)`, `created_at / updated_at`, `uniqueIndex loan_facilities_snapshot_ref_unique on (snapshot_id, entity_id, facility_reference)`, `index loan_facilities_group_idx on (security_group, snapshot_id)`
- `loan_rates` — DEBT-002 fixed/floating split and rate; DEBT-004 interest-rate sensitivity input. One row per tranche, so a part-fixed/part-floating facility is two rows and sensitivity can reprice only the floating (and near-roll fixed) principal.
  - columns: `id (text pk)`, `facility_id (text notNull → loan_facilities.id)`, `rate_type (text enum fixed|floating notNull)`, `principal_amount (text notNull, decimal string — this tranche's share of drawn)`, `annual_rate_percent (text notNull, decimal string)`, `margin_percent (text, decimal string)`, `fixed_until_date (text, date-only — null for floating)`, `source_row_ref (text)`, `created_at / updated_at`, `index loan_rates_facility_idx on (facility_id)`
- `loan_covenants` — DEBT-004 — versioned, effective-dated covenant configuration. This table is the reason no 55% appears anywhere in code: the threshold is data, scoped to an entity or a security group, with an approver and an effective window. Same 'config not constant' pattern as variance_thresholds.
  - columns: `id (text pk)`, `scope_type (text enum entity|security_group notNull)`, `scope_ref (text notNull — entities.id or the security_group string; deliberately not an FK, mirroring the GLOBAL_THRESHOLD_SCOPE sentinel reasoning)`, `lender_name (text notNull)`, `covenant_code (text notNull — LVR, DSCR, ICR)`, `operator (text enum max|min notNull)`, `threshold_value (text notNull, decimal string)`, `threshold_unit (text enum percent|ratio|amount notNull)`, `test_frequency (text enum monthly|quarterly|semiannual|annual notNull)`, `effective_from (text notNull, date-only)`, `effective_to (text, date-only — null = current version)`, `approved_by_email (text notNull)`, `source_reference (text — facility agreement clause)`, `created_at / updated_at`, `index loan_covenants_scope_idx on (scope_type, scope_ref, covenant_code, effective_from)`
- `loan_security_valuations` — DEBT-004 LVR denominator. Not in the spec's 14.8 list but LVR is unbuildable without it: Xero holds no property values. Latest-valuation-per-property-wins, resolved the same way bank_balance_snapshots resolves latest balance (order by date then created_at).

Evidence columns and the approval triple are on the row itself so an adjustment cannot be applied without both; lib/debt/lenderAdjustments.ts refuses to apply any row that is not status='approved' with a non-null evidence_ref inside the requested period.

- GET /Reports/TrialBalance (accountingApi.getReportTrialBalance) — the only genuinely new call. Supplies closing balances for loan liability accounts and YTD interest expense in one request per entity per sync. Scope accounting.reports.trialbalance.read: present in read_core_v1.

Module H does not call it — security values come from the client's valuations, not Xero. Do not let LVR work drift into the Assets API without a scope-profile change and a fresh compliance review.

### Depends on

- Module A — reuses variance_thresholds + lib/thresholds.ts for DEBT-003 exception flagging, and the /api/cash-position row shape (bank_balance_snapshots totals) as the cash input to 'liquidity after committed payments'.
- app/api/xero/sync/route.ts — must be extended to fetch non-bank accounts and the Trial Balance before DEBT-003 can compare anything. This is the one existing file Module H changes.

### Blocked on client decisions

- The approved Loan Register template (Appendix D item 12). The CSV parser cannot be written against a guess: needs the real headers, whether a part-fixed/part-floating facility is one row with two rate columns or two rows, and whether the file is CSV or XLSX. If XLSX-only, that is a new dependency decision (SheetJS) or a request for the client to export CSV.
- Covenant rules per lender and security group (spec section 3047 item 13): which covenants exist (LVR, DSCR, ICR), operator, threshold, unit, test frequency and effective dates. The 55% is explicitly not to be hard-coded, so it must arrive as data before loan_covenants can be seeded.
- The ASB charging group definition: which entities and which properties sit inside it, plus approved security valuations with as-at date and basis. Without the valuation denominator there is no LVR at all — this is the single hardest blocker in Module H.
- DSCR inputs. DEBT-004 says 'where inputs are approved' — need the earnings base (EBITDA before or after lender adjustments?) and whether debt service is contracted or actual P&I. Until answered, DSCR ships as a covenant_code the config table accepts but the engine returns 'inputs_unavailable' for.
- Lender adjustment policy (spec table row at line 3335): the approved add-back/removal list, what evidence each type requires, who may approve, and whether approval is per period or standing.
- Facility-to-Xero account mapping per entity: which Xero loan liability account code and which interest expense account code each facility corresponds to, and which existing entity_bank_accounts rows flagged is_loan_facility map to which register facility. DEBT-003 compares nothing without this.
- Source of the 'committed payments' list for liquidity after committed payments — approved Xero bills awaiting payment, or a separate manual payment schedule.
- Interest comparison period basis: whether comparing register expected interest against a Xero year-to-date figure is acceptable, or a specific period range is required (which upgrades the sync from Trial Balance to a date-ranged P&L call).

### Risks

- Sign convention on the Trial Balance parser is the highest-consequence unknown. Xero returns debit and credit as separate columns and liability accounts sit on the credit side; a parser that guesses will silently flip every loan balance and make every covenant look fine. Needs a Demo Company fixture test before anyone trusts a number — the same 'ASSUMPTION, unverified' caveat already written into parseBankSummaryClosingBalances applies here with real money attached.
- Xero has no concept of a facility. A loan liability account balance includes accrued interest, capitalised fees and repayments not yet posted, so DEBT-003 will rarely show a nil variance. Without per-entity threshold tuning the comparison produces constant noise and gets ignored. Reusing variance_thresholds means the tuning mechanism already exists, but the values will need to differ substantially from the cash ones.
- Mixed as-at dates. A covenant computed from a month-old register snapshot plus this morning's Xero balance is arithmetically valid and financially misleading. Mitigation is to return oldestSourceDate on every /api/debt/position row via lib/dates.ts oldestDateOnly, exactly as cash-position does, and to refuse to render a covenant result without showing it.
- Multi-tranche facilities where tranche principals do not sum to the drawn balance. facilityView returns a warning rather than a weighted average computed over an inconsistent base — but if the register commonly disagrees with itself, the fixed/floating split in DEBT-002 is unreliable and the client has a data-quality problem to fix, not a code problem.
- Currency. Everything assumes NZD; Money.assertSameCurrency throws hard on a foreign-currency facility. That failure is correct but loud, and a single USD facility in the register will 500 the whole position route until multi-currency handling is designed.
- Scope creep from DEBT-005 into write-back. 'Approved adjustment' reads to some stakeholders as 'post it to Xero'. No write scope exists anywhere in this build; the adjustment schedule is a reporting overlay only. Worth stating in the UI copy so the expectation never forms.
- Extending app/api/xero/sync/route.ts to fetch all account types materially increases rows in xero_accounts. The cash-position lookup by (entityId, code) stays safe because Xero account codes are unique per organisation and the unique index is on xeroAccountId, but the sync run's records_read count and its meaning change, and any dashboard counting synced accounts will move.
- Six of the eight blockedOnClientData items are hard blockers on real output, not on scaffolding. The schema, routes, libs and tests can all be built and unit-tested against fixtures without client data, but the module produces no trustworthy number until the register template, covenant rules, charging-group membership and valuations arrive. Sequence the client request before starting, not after.

## Module I — Attachments and Document Extraction (DOC-001..DOC-004)

Ramwall's evidence layer: for every invoice, bill, bank transaction and manual journal in Xero, the app records what documents are attached without pulling the files down, then fetches the actual bytes only when someone opens the evidence or asks for a document to be read. Once a file is cached it extracts the fields that matter (invoice number, date, supplier, GST, total), cheapest method first, and shows them for a human to confirm or correct before they count for anything. Nothing is ever uploaded or written back to Xero — this build has no write access at all.

**Value:** medium  |  **Effort:** 11 days

### Risks

- Rate limits are the real constraint, not storage. Attachment enumeration costs one call per parent document against 60/min and 5000/day per tenant. A first backfill across five entities can exhaust a day's budget before it finishes. Mitigations: filter HasAttachments==true, watermark on UpdatedDateUTC, hard per-run call cap, resume from the last sync_runs cursor.
- Unbounded cache growth. rawFileStore has no size cap and no retention job, and the retention policy is a client blocker. A bulk download can fill local disk (and later, R2 spend). Mitigation: refuse to download above a content_length ceiling, cap bytes per run, surface cached_bytes totals on the /xero page.
- The runner is a second moving part. If nobody starts it, jobs sit at 'queued' forever and silently. Mitigation: surface queued-job age in the UI the same way connection staleness already is, and treat a stale queue as a visible exception rather than an empty list.
- Content-type mismatch (spec 39.7). Xero's mime_type is a claim from an uploader, not a fact. Bytes must be magic-byte sniffed before reaching any PDF or OCR parser, and served back under a fixed allowlist with Content-Disposition: attachment. Never inline-render an attachment — an SVG or HTML file served inline is stored XSS against the finance dashboard.
- Bytes can change under a stable Xero attachment id. Only the checksum notices. cached_checksum must be re-verified on a cache_refresh trigger rather than assumed valid, or a replaced document silently keeps serving old evidence.
- Prompt injection from document text (spec 39.7) the moment tier 5 turns on. Extracted text is attacker-controlled input arriving inside a finance system — it must never be concatenated into an instruction position.
- DOC-002 tiers 4 (OCR) and 5 (LLM) are deliberately NOT built in this estimate. Xero-generated PDFs carry a text layer, so tiers 1-3 cover the common case; the pipeline returns status='needs_ocr' instead of guessing. Upgrade path: add the tier to extractionPipeline.ts and the parser to the runner. Ceiling: genuinely scanned supplier invoices will queue as needs_ocr and go nowhere until then.
- Estimate risk against the spec: Phase 9 quotes 4-8 days, but that bundles AI and excludes the metadata sync and the runner interface entirely. 11 days is the honest number for DOC-001..004 with tests.

## Module J — Optional AI Assistance (AI-001 … AI-004)

Adds an optional AI layer that writes plain-English commentary over figures the platform has already calculated — the app runs exactly as it does today with AI switched off, and switching it on never changes a number. Every invocation is recorded with its provider, model, prompt version, the source records it cited, token count and NZD cost, so the board can see what the AI was asked and what it cost. The AI is structurally incapable of touching Xero: it reads only local normalised data, and a deterministic validator rejects any output containing a figure that is not already in the supplied fact set.

**Value:** medium  |  **Effort:** 7 days

### Tables

- `ai_providers` — SEC-006 approved provider register plus AI-001 feature gate. Deliberately mirrors the xero_apps registry shape: secret refs (env var NAMES, never values), an approval status the client signs off, and an enabled flag. Expected to hold one row.

### Risks

- Four of the five AI-002 approved uses have no upstream data in this build (B, E, I and L are all unbuilt). Delivering 'Module J' as complete without that caveat would misrepresent scope: what ships is the full control plane plus one live use — cash-position narrative.
- Number-guard false positives are the main usability risk. A narrative that rounds ('about $1.2m' against a fact of 1,234,567.89) or counts ('three entities breached') will be rejected. Mitigation: rejection is recorded as number_guard_rejected with the offending token and nothing is shown — it fails loudly, never silently passes an unverified figure. Expect to tune an allowlist for years, counts and ordinals during the first week of real use.
- Prompt injection (spec 2696). Low today because cash facts are numbers and entity short codes, but the fact builder must stay allowlist-based rather than passing through free text — the moment Module I feeds document text in, an unstructured field becomes an instruction channel.
- ai_runs.output_json holds narrative text derived from financial data, so it is financial-adjacent data at rest and falls under SEC-005 retention. It needs a retention decision, not just a table.
- Cost telemetry is only as accurate as the two rate columns on ai_providers. A provider price change silently skews reported NZD cost until someone updates the row — the ledger will look right and be wrong.
- The no-write gate is structural, not just policy: lib/ai/* must never import lib/xero/gateway.ts or appRegistry.ts, since buildXeroClient is the only path to a Xero call. Worth one cheap import-graph assertion in tests so a future refactor cannot quietly open that path.
- A provider returning prose instead of JSON, or truncating mid-object, is normal operational noise. Handled as provider_error with no partial output persisted, but it means the feature is visibly flaky to end users on a bad provider day and the UI should say so rather than showing a spinner.

## Module K — Proposed Fixes and Controlled Write-Back

Module K turns "we found a problem in Xero" into a reviewable, approvable, auditable proposal — never into an automatic change. A preparer creates a proposed fix (recode a draft invoice, raise a draft recharge, draft a manual journal), the system deterministically validates it, an approver with the right delegation signs it off, and only then is it queued for a single idempotent write that is re-checked against live Xero immediately before sending and read back immediately after. In this build the execution half is deliberately dark: no write scopes exist anywhere, so every proposal stops at "queued" with a named reason, and what the client gets today is a controlled worklist with a full approval and evidence trail.

**Value:** medium  |  **Effort:** 10 days

### Tables

- `proposed_actions` — WRITE-001/004 — one row per proposed fix, carrying the whole payload, the state machine and full Xero lineage. This is the only place a proposal exists; there is no path from detection or AI output into action_executions that does not create a row here first.
  - columns: `id (text pk, nanoid)`, `entity_id -> entities.id`, `action_type enum: invoice_recode | draft_recharge_invoice | draft_manual_journal | manual_journal_update | contact_upsert | draft_evidence_attachment (WRITE-002 minus payroll; WRITE-003 enforced by absence from this enum)`, `payload_schema_version text (e.g. 'k1')`, `xero_app_id -> xero_apps.id`, `connection_id -> xero_connections.id`, `tenant_id text  [these three + sync lineage satisfy spec 10.5]`, `source_kind enum: cash_variance | manual | rule`, `source_ref text nullable (entity_bank_accounts.id for a CASH-005 variance today; becomes exceptions.id when Module H/J lands)`, `evidence_refs text JSON array of {type,id} — bank_imports.id / sync_runs.id / xero_accounts.id, i.e. the exact CASH-006 evidence shape`, `xero_resource_type text nullable ('Invoice' | 'ManualJournal' | 'Contact')`, `xero_resource_id text nullable`, `resource_status_at_proposal text nullable ('DRAFT')`, `source_updated_at_at_proposal text nullable (Xero UpdatedDateUTC seen when snapshotting — the WRITE-005 change detector)`, `before_state text JSON`, `after_state text JSON`, `amount_impact text decimal string nullable`, `tax_impact text decimal string nullable`, `tracking_impact text JSON nullable`, `currency text notNull default 'NZD'`, `accounting_reason text notNull`, `rule_id text nullable`, `rule_version text nullable`, `prepared_by_email text notNull`, `required_approver_role enum: approver | senior_approver`, `materiality_band enum: low | medium | high`, `risk_rating enum: low | medium | high`, `idempotency_key text notNull UNIQUE (WRITE-006 layer 1 — the database constraint)`, `payload_fingerprint text notNull (sha256 of before_state+after_state+amount_impact; - `action_approvals` — WRITE-008 — immutable approve/reject decisions. Separate table, not a column on proposed_actions, because segregation of duties needs to know who decided and because two approvals may be required above materiality.
  - columns: `id (text pk)`, `proposed_action_id -> proposed_actions.id`, `decision enum: approved | rejected`, `decided_by_email text notNull`, `decided_by_role enum: approver | senior_approver`, `comment text nullable`, `payload_fingerprint text notNull (copied from the proposal at decision time; the executor refuses if the proposal's fingerprint no longer matches — that is edit-after-approval)`, `created_at text notNull  [no updated_at: approvals are append-only]`, `uniqueIndex action_approvals_one_per_approver (proposed_action_id, decided_by_email)`, `index action_approvals_action_idx (proposed_action_id)`
- `action_executions` — WRITE-005/006/007 — one row per execution attempt, including attempts that never reached Xero. Holds the revalidation verdict, the idempotency key actually sent, the Xero response and the read-back verification result. Spec 14.9's separate verification_results table is folded in here: one attempt has exactly one verification, so a join buys nothing.

- `approval_policies` — WRITE-008's 'configurable materiality' and delegated threshold. Keeping it separate from users.role is the point: 'administrator manages configuration but cannot bypass accounting approval' falls out for free, because admin on its own grants no approval right.
  - columns: `write_back_role text notNull default 'none', enum: none | preparer | approver | senior_approver`

### Routes

- `POST /api/writeback/proposals` — Create a proposal. Snapshots before-state from Xero via getAuthenticatedClient on the read_core route, runs lib/writeback/validate.ts inline (status -> validated or fail), mints the idempotency key and fingerprint, writes lineage. Requires write_back_role 'preparer' or above — NOT requireSession('admin').
- `GET /api/writeback/proposals` — List the queue with ?entityId=&status=&actionType= filters. Viewer role, same as /api/cash-position.
- `GET /api/writeback/proposals/[id]` — Full detail: before/after diff, evidence_refs resolved to their bank_imports and sync_runs rows (same drill-through shape as CASH-006), approvals, execution attempts, and the rollback entry for its action type.
- `PATCH /api/writeback/proposals/[id]` — Edit while in draft/validated/pending_approval. Any edit recomputes payload_fingerprint, resets status to draft and voids existing approvals — this is why there is no action_payload_versions table.
- `POST /api/writeback/proposals/[id]/approve` — Body { decision: 'approve' | 'reject', comment }. Runs lib/writeback/approvals.ts: role vs required_approver_role, materiality from approval_policies, self-approval/SoD, expiry, fingerprint match. On the final required approval it also moves the proposal to queued — WRITE-001 needs the states, not a separate HTTP verb per state.
- `POST /api/writeback/proposals/[id]/execute` — The gated executor. Calls lib/writeback/executionGate.ts first; in this build it always fails closed and returns 409 with the reason, writing an action_executions row with outcome='not_attempted' and revalidation_status='fail_write_disabled' or 'fail_scope_missing'. The full revalidate -> write -> read-back path behind the gate is written and unit-tested against a faked client.
- `GET /api/writeback/action-types` — Serves the lib/writeback/actionTypes.ts registry as the governance-readable WRITE-002/003/009 matrix: permitted types, prohibited types with reasons, required scopes, editable statuses, and the per-type rollback rule.
- `GET /api/writeback/policies` — Read approval materiality config. Mirrors GET /api/thresholds exactly.
- `PUT /api/writeback/policies` — Upsert an approval policy by (entity_id, action_type) with onConflictDoUpdate, audited with from/to values — same pattern as POST /api/thresholds. Admin role.

### Logic modules

- lib/writeback/actionTypes.ts — pure registry: per action type its Xero resource, required scopes, editable statuses, required approver floor, and its rollback rule {automated, statusPreconditions, compensatingAction, manualInstruction, approvalRequired}. WRITE-009's 'do not use one generic Undo' is enforced by there being no generic undo function, only this per-type data. WRITE-003 prohibited types live here as a PROHIBITED_ACTIONS map that exists only to produce a clear refusal message.
- lib/writeback/validate.ts — pure deterministic validation (REM-001): zod payload schema per action type, manual journal debits must equal credits via Money.compare, amount/tax/tracking internal consistency, account code must exist in the entity's xero_accounts rows, target status must be in the type's editableStatuses. Returns {status, detail} — no DB writes, no Xero calls.
- lib/writeback/approvals.ts — pure WRITE-008 policy, shaped exactly like lib/xero/compliance.ts (approvalFailureReason(...) -> string | null plus an assert wrapper): resolves approval_policies entity-over-group with the same shape as resolveThreshold, decides required_approver_role from amount_impact via Money, and refuses self-approval, duplicate approval, expired proposals and fingerprint mismatch.
- lib/writeback/idempotency.ts — pure: logicalActionId(entityId, actionType, xeroResourceId, payloadFingerprint) -> deterministic sha256 key capped at 128 chars (Xero's limit), and payloadFingerprint(before, after, amount). Same node:crypto createHash already used in lib/rawFileStore.ts.
- lib/writeback/revalidate.ts — pure WRITE-005 decision function: given the proposal row, the freshly-resolved route and the just-read Xero resource, returns one of the revalidation_status values. All I/O stays in the caller so every branch is testable without a network.
- lib/writeback/verify.ts — pure WRITE-007 comparison: expected after-state vs the read-back resource, field by field, monetary fields compared through Money not string equality. Returns {verificationStatus, detail}.
- lib/writeback/executionGate.ts — the hard no-write gate. Three independent fail-closed checks: WRITE_BACK_ENABLED env flag; resolveXeroRoute(entityId, 'controlled_write') (already fails closed today — no controlled_write assignment exists); and every scope in the action type's requiredScopes must be present in the resolved xero_authorizations.granted_scopes. Any miss throws, nothing is sent.
- lib/writeback/execute.ts — the only impure module: gate -> GET the resource via getAuthenticatedClient -> revalidate -> mutating call with idempotencyKey -> read-back GET -> verify -> write the action_executions row and advance proposed_actions.status. Never mints a new key on an ambiguous error; sets outcome='ambiguous' and status='manual_follow_up' so a human reads Xero first.

### UI

- app/writeback/page.tsx — the proposal queue: filter by entity, status and action type, columns for amount impact, required approver, expiry, and a badge for anything past expires_at. Reads /api/writeback/proposals only; no policy logic in the component (REM-001).

- NZ chart-of-accounts and tracking conventions for a recharge invoice: which account code, which tracking category, which tax type. validate.ts cannot check a recode without knowing what a correct code looks like.
- Whether the Ramwall Xero orgs hold the Payroll NZ product at all — decides whether timesheet action types are ever K's problem or stay entirely in Module L.
- Signed-off rollback / compensating procedure per approved action type (spec decision item 27). WRITE-009 requires it documented and tested before production enablement, and it is accounting judgement, not a coding decision.
- Retention rule for before_state / after_state snapshots — they hold client financial detail indefinitely with no policy today.

### Risks

- The executing half ships dark. With read_core_v1 the only profile, the honest deliverable is a proposal queue with an approval trail that an accountant then applies in Xero by hand. If the client expects automation on delivery, that expectation has to be reset before the build starts, not after.
- Xero's Idempotency-Key window is 24 hours. A proposal that sits in approval longer than that loses WRITE-006 layer two and falls back to the unique constraint plus the pre-write GET. expires_at should be set inside 24h of queueing, or the reduced guarantee has to be accepted and documented.
- Ambiguous failures (network timeout after Xero accepted the request) are the dangerous case. execute.ts must never mint a fresh key; it sets outcome='ambiguous' and stalls the proposal for a human read of Xero. A flaky connection therefore produces manual work, by design.
- updateInvoice against a non-DRAFT invoice can partially apply. The editable-status precondition is the only guard, and it is checked from a snapshot that is stale the instant it is taken — which is exactly why WRITE-005 re-reads immediately before the write. Any shortcut here is the bug that ships.
- Read-back verification can pass a naive field compare while being semantically wrong: Xero recomputes tax and rounds to its own precision. verify.ts must compare monetary fields through Money, never string equality, or every recode will look like a mismatch.
- source_ref is untyped text today. When Module H/J lands with a real exceptions table this needs a migration to a proper FK — cheap now, less cheap after a few hundred rows.
- Adding controlled_write_v1 scopes to an existing app requires reconsent on every connection on that app. That is a coordinated rollout event across all entities, not a deploy — schedule it as one.
- lib/xero/reports.ts already carries an unverified assumption about Bank Summary column order. Any proposal sourced from a cash variance inherits it, so a wrong column would generate confident, wrong proposed fixes. Verify against a live Demo Company response before wiring cash_variance as a proposal source.
- approval_policies and variance_thresholds will look like duplicates to a reviewer. They are not, and the comment on each table has to say so, or someone will 'simplify' them into one and silently change what counts as an exception.
